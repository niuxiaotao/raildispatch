# 方向层：用图，而不是几何

> 本文件记录一次**结构性决定**。方向相关的问题在本项目里消耗了最多轮次，
> 原因不是某个 bug，而是**架构选错了层级**：用几何去逼近一个拓扑问题。

## 问题

驾驶台需要知道"车往哪边走"（用于信号搜索、道岔瞄准、通道映射）。
原先的实现是四层推导：

```
方块 FACING → forwardHeading（世界向量，曾从位移"学习"）→ reversing 判定 → 取反
```

**每一层都可能错，并且错了以后互相掩盖**：

| 层 | 失效方式 |
|---|---|
| `FACING` | 六面同贴图时玩家无法判断哪面是前（现已加前脸贴图缓解） |
| 从位移学习世界向量 | 一次错误判定会被"自洽地"学进去并持久化；读档后为空；低速时是噪声 |
| `reversing` 判定 | 与信号搜索的时间不同步（每段一次 vs 每 5 秒） |
| 取反 | 上面任一错，取反后正好反向 |

## 决定

**行进方向由图给出，不再推导。**

```
车在图上的哪条边  +  进路要去的下一个节点  ⇒  行进方向 = 朝向那个节点
```

这是一个**拓扑事实**，因此：

| 老问题 | 为何消失 |
|---|---|
| 读档后"未知" | 图没有"未知"状态 |
| 低速时方向是噪声 | 与速度无关 |
| 倒退时读反方向 | "朝哪走"由进路给出，不存在"反" |
| 方向未定时的时序窗口 | 方向在**进路授予时**就已知 |
| 结构旋转后失效 | 世界坐标不再参与 |

## 通道映射：不学，约定即契约

**驾驶台不判断"哪条通道能让车朝那个节点走"** —— 那是玩家的事，因为**我们已经用前脸贴图告诉过他那一边是正面**：

```
玩家把斜纹面朝行进方向摆放 → 按这个约定接线
⇒ 驾驶台只需服从约定：forward 通道 = 斜纹方向
```

**为什么不做标定**：标定会引入一套新状态（标定值、何时失效、读档后怎么办），而**一个不需要的机制就是一份不需要的负担**。约定是**可见的**（贴图）、**在放置时确定的**、**玩家可以直接检查的** —— 这比任何自动学习都可靠。

**只有一种情况需要"反向"**：进路要求车朝斜纹的**反方向**走。那时用齿轮箱的**另一侧**（`backward` 通道），而"是否需要反向"由 **`FACING` 与目的地方向**的夹角决定 —— 两个操作数都是**稳定量**（方块朝向、进路目的地），不含任何来自运动的测量。

## 迁移顺序

1. **不需要改 api。** "进路的下一节点"本来就可以在**使用处**由图得到：车的位置 → `graph.locateNode` → 沿 `getConnectionsFrom` 前进，第一个节点就是下一节点。`walkToNextSignal` 已经是这个形状。
   这比给 `RouteGrant` 加字段更小：**不用动 `TrackNetwork`、`CreateTrackNetwork`、`DispatchCenterEntity` 三处签名**（那是本项目断编译最多的一类改动）。
2. 信号搜索、道岔瞄准改用该节点，删除 `heading` 相关的筛选。
3. 方向只保留一处来源：**方块 `FACING`**（玩家按可见约定摆放）。删除任何从运动"学习"方向的逻辑。
4. `reversing` = `dot(FACING, 目的地方向) < 0`；两个操作数都是稳定量，不需要标定、不需要历史。

## 教训（值得单独记住）

**当一个问题反复以不同症状出现时，先怀疑层级选错了，而不是继续修症状。**
本项目里"方向"以四种面貌出现过（信号读反、道岔扳错、起步反向、低速乱跳），
而它们全部源于同一个层级错误：**用连续的几何量去表达一个离散的拓扑关系**。
