# 驾驶台操控规格（对齐原版 Create）

## 1. 交互（对齐 Create 的 Train Controls）

| 操作 | 行为 |
|---|---|
| 空手右键 | **接管驾驶**（开始显示 HUD）；再次空手右键 = **交还**（HUD 消失，恢复自动/待机） |
| 手持时刻表右键 | 装入时刻表（并**同步给同车的另一台**，见 §3） |
| Shift + 空手右键 | 取回时刻表 |
| 潜行 + 手持时刻表右键 | 装入但不接管（便于布设） |

要点：**不再打开 GUI**。屏幕上的速度/灯色改由 HUD 呈现，因此原菜单的 `ContainerData` 同步通道随之作废，
必须补一条网络通道（§4）。**在 HUD 可用之前不要删除菜单代码**，否则会失去唯一的状态可观测手段。

## 1b. 接管后的键盘驾驶（W 前进 / S 后退与制动）

要求：接管后按 **W 前进**、按 **S 后退/制动**。

### 关键结论：**必须新增客户端到服务端的网络包**（此前的判断是错的）

先前认为"原版已同步玩家前后输入，读服务端 `player.zza` 即可"，**已在游戏里证伪**：

- 实测：接管后按住 W，日志中 `zza=0.00`（读数一直为零）；
- 离线核对：`net.minecraft.world.entity.player.Input` 在 **1.21.1 不存在**（更高版本才加入），
  `Entity.input`、`LivingEntity#getLastClientInput` 同样不存在。

即 **1.21.1 的服务端不掌握玩家的 W/S 状态**，玩家的移动靠位置包直接驱动。因此 W/S 驾驶
**必须**由客户端读取按键并发送给服务端：

```
客户端 ClientTickEvent：接管某台驾驶台时读 options.keyUp / keyDown
                       → 仅在输入变化时（或按 4Hz 节流）发送 CabControlPayload(驾驶台坐标, 前进, 后退)
服务端 handle：校验玩家在附近、且是该台的接管者 → 写入该台的"手动输入"，由 manualControl 读取
```

因此**第 4 步的网络包不再只有 HUD 的 S→C 方向，还包含这个 C→S 方向**；工作量回到原先估计。
教训：用一条诊断日志（`zza=`）在动手之前证伪假设，比先写完整套控制再发现输入根本读不到便宜得多。

### 必须解决的一个问题：**玩家会一边"开车"一边走**

读 `zza` 的同时，玩家自己也在按原版逻辑前后走动（甚至被车带着位移）。原版 Create 的做法是把玩家**装到车上**，
而对一个物理结构没有可直接骑乘的实体，所以要么：

1. **取消接管玩家的移动**（服务端把其位移清零 / 拦下移动包）—— 最小改动，但属于"和原版移动系统对着干"；
2. **让玩家坐进驾驶台**（若 Sable 提供座位/乘客挂载能力）—— 更接近原版，需要先确认 API；
3. **不干预移动**，仅把 `zza` 当作控制信号 —— 最简单，但玩家会边走边开车，体验明显不对。

**建议先做 (1)**，并把 (2) 记为后续改进；实施前需要确认一条：接管玩家的 `zza` 在**站着不动（未产生位移）时仍会被同步**，
否则要用 `ServerboundPlayerInputPacket` 的输入标志位代替。这一点我无法离线确认，必须在游戏里验证。

### 控制模型：油门设定值 + 自研制动，牵引改走 DriveByWire 红石通道

用户确认的四条：

1. **保留自研制动**（刚体减速模型）。Simurail 自带刹车约 1 tick 停住，无法用于可控减速，这条不变。
2. **删除 bogey API 的牵引功能**（`setRemoteStrengthOverride` 等）。它非负，表达不了反向，而且是我逆向出来的接口。
3. **控制台改为"加/减速度"，而不是按键直接前进/后退。**
4. **速度 > 0 时，S 为制动。**

据此，手动控制不再是"按 W 就前进"的开关，而是一个**油门设定值**：

```
W 按住 -> 设定值上升（加速度为正，按速率积分）
S 按住 -> 速度 > 0 时制动；速度 ≈ 0 时设定值下降（可用于反向）
松开   -> 设定值保持，由制动/阻力决定实际速度
```

即 **W/S 操纵的是"加速度指令"，而不是"速度方向"**。这样反向自然出现（设定值可为负），不需要 bogey API 的方向通道。

**牵引输出改为 DriveByWire 红石通道**（通道名与取值见 `_recon/drivebywire-api.md`），
制动力仍由本模组的刚体模型施加。

### 实施顺序（有依赖，不能颠倒）

1. **先**接入 DriveByWire 通道发射，让牵引有新的出路；
2. **再**删除 bogey API 的牵引调用。

**顺序颠倒会让车辆在中间状态下完全无法驱动** —— 我不做那种"先拆掉能用的，再装上新的"的改法。
在两个通道并存的那一步，两者都工作，可以对比验证。

### 移动抑制：在客户端清零移动冲量

接管期间玩家不应走动。做法是在 NeoForge 的 `MovementInputUpdateEvent`
（`LocalPlayer.aiStep` 中、冲量算好之后、实际生效之前）把 `Input.forwardImpulse` / `leftImpulse` 清零。

- **不在服务端清零位移** —— 那会造成客户端预测/服务端纠正的橡皮筋感；
- **不会丢掉我们自己的输入** —— 按键是从 `options.keyUp` / `keyDown` 直读的，不依赖这两个冲量；
- 已对着 NeoForge jar 核对：`MovementInputUpdateEvent.getInput()` 返回 `net.minecraft.client.player.Input`，
  其 `forwardImpulse` / `leftImpulse` 均为 `public float`。

## 2. 双控制台 / 双向


- 一辆车可以装**两个**驾驶台，各自朝一个方向（车头/车尾），用于双向运行。
- 归属判定：两台驾驶台通过**同一个物理车**（`PhysicsBridge.vehicleOf` 返回同一 sub-level）判定为**同车**，
  以车辆 UUID 为键成组。
- **角色（决定性的规则，由用户确认）：朝向目的地的那台控制台，就是当前控制的那台。**
  另一台待命。也就是说，"哪台在开车"由**它与目的地之间的朝向关系**决定，而不是由玩家点了哪台决定。
  - **目的地方向**：`destination - vehicle.position()` 取水平方向（有进路时用进路首段更准）。
  - **每台的世界朝向**：方块的 `FACING` 是**结构内局部朝向**，必须经车辆姿态变换到世界空间：
    `worldFacing = subLevel.logicalPose().orientation().transform(localFacing)`。
    **不要**拿方块 `FACING` 直接与世界方向比较 —— 这正是本项目在信号筛选上犯过的错。
  - **判定**：`dot(worldFacing_of_cab, toDestination) > 0` 的那台为激活；两台都 > 0 或都 ≤ 0（极端几何）
    时取点积较大者，并在日志中说明，避免出现"没有一台在开车"。
  - 两台同时下发指令在技术上可行（Simurail 按控制器坐标记账），但**语义上必须只有一台在开车**，
    否则会出现两个控制器互相抵消的抖动。
- **朝向**：不要用方块的 `FACING` 属性判断"哪台朝前" —— 结构被组装后，方块位于 plot 坐标系，
  与世界方向无关（这是本项目反复踩到的坑）。正确做法是用 `subLevel.logicalPose().orientation()`
  把方块在结构内的**局部偏移/朝向**变换到世界空间，再与车辆行进方向比较。
- 选择哪台激活：**朝向目的地的那台**（见上，这是用户确认的规则）。
  玩家可以接管任意一台，但**下令的永远是朝向目的地的那台**。

## 3. 时刻表同步

- 装入：任一台装入时刻表 → **复制到同车另一台**（写入对方的 `TRAIN_CAB` 物品槽），双方内容一致。
- 取出：任一台 Shift+右键取出 → **两台都取出**（避免留下不一致的半份）。
- 运行时：**只有激活的那台**推进 `Progress`；每次推进后**同步回另一台**，这样换向之后另一台能接着跑。
- 冲突：若两台都已装有**内容不同**的时刻表，以**激活的那台**为准，并覆盖另一台（并记一条日志说明）。

## 4. 状态同步（HUD 的前置）

`ContainerData` 随菜单一起失效，因此新增：

- `CustomPacketPayload`：`CabStatusPayload`（驾驶台坐标、速度 b/s、`SignalAspect`、状态枚举）
- 服务端**每 5 刻**向**约 64 格内**玩家发送（不是每刻、不广播全服）
- 客户端保存"最近的驾驶台状态"，`LayeredDraw.Layer` 读取并绘制
- 仅在**当前玩家接管了某台驾驶台**时显示

## 5. HUD 内容

- **速度**：数字 + 单位（格/秒；可换算 km/h 显示）
- **信号**：图标（绿/黄/红/无信号），需新增 4 张 16×16 贴图，走已有的 `tools/make-textures.ps1` 流程
- 位置与样式对齐原版 Train Controls HUD（右下角）

## 6. 数据

驾驶台已持久化：`State`（读档时强制回到 `IDLE`）、`WaitTicks`、`WaitUntil`、`ScheduleInstalled` 等。
新增需要持久化的：**车辆 UUID**（用于双台配对；现在每周期通过 `vehicleOf` 反查，代价是每周期一次 plot 遍历）、
以及**激活角色**（`ENGAGED`/`STANDBY`）。

## 7. 实施顺序

1. 交互三态（接管/装入/取出）+ 停止打开菜单（**保留菜单代码**）
2. 双台配对与角色（含 plot 空间朝向换算）
3. 时刻表同步
4. 网络包 + 客户端缓存
5. HUD 层 + 4 张信号灯贴图
6. 删除菜单/屏幕（此时 HUD 已可替代）
